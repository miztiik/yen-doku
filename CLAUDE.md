# CLAUDE.md - Yen-Doku Engineering Contract

**Last Updated**: 2026-07-05

Non-negotiable contract for any human or AI agent working in this repo. If a design choice conflicts with simplicity or correctness, choose correctness.

## 0. User Approval

User approval supersedes every rule in this file. Amend conflicting rules in the same change.

## 1. What Yen-Doku is

- A daily Sudoku game: one classic 9x9 puzzle per difficulty per day, plus five overlapping Gattai (Samurai) variants.
- Two runtimes that never overlap: **Python in GitHub Actions** generates and validates puzzles; **JavaScript in the browser** renders and plays them.
- Deployed as a static bundle on GitHub Pages from `docs/`. No backend, database, or external API.

See [docs/architecture/overview.md](docs/architecture/overview.md).

## 2. Holy Laws

1. **Static-first.** The deployed game is a static bundle on GitHub Pages; everything it needs at runtime ships in the repo. No production backend.
2. **Two runtimes, strict boundary.** Python runs only in CI (generate, solve, validate, score). JavaScript runs only in the browser (render, interact, persist) and is never authoritative - the committed JSON is the source of truth.
3. **Exactly one solution.** Every generated puzzle is validated to have a unique solution; a validation failure fails CI and blocks the commit. A silently corrupt puzzle is never shipped.
4. **Contracts before logic.** Every persisted shape (puzzle JSON, localStorage save data) has a documented schema before logic is written. See [docs/reference/data-contracts.md](docs/reference/data-contracts.md).
5. **Determinism.** Generation is date-seeded and idempotent - same input, same output.
6. **Structural fixes only.** No band-aids or "temporary" hacks; escalate the correction level instead.
7. **Tunables are not duplicated.** Difficulty thresholds and clue ranges live in [scripts/difficulty.py](scripts/difficulty.py) and are read from there, never re-hardcoded in the client (which only reads the `difficulty` field already in the puzzle).
8. **Open source first.** Prefer mature OSS (e.g. py-sudoku) over custom builds; the browser client ships zero runtime dependencies.
9. **Tests ship with the feature.** A behaviour-changing commit lands with tests; the full suite is green at merge.
10. **ASCII only** in repo text (docs, code comments, commit messages): write `-`, `->`, `>=`, "section". Applies going forward; no retroactive fixing. The public [README.md](README.md) is the exception and may use richer typography.

## 3. Technology Boundaries (strict)

- **Python (CI only):** `scripts/` - generation, solving, validation, difficulty scoring. Never runs in the browser.
- **JavaScript (browser only):** `docs/` - rendering, interaction, optional non-authoritative client-side solving. Never generates or validates puzzles authoritatively.
- No external APIs, databases, or paid services. GitHub free tier only (Actions + Pages).

## 5. Layer and Dependency Rules

- `docs/` (browser code) MUST NOT depend on a runtime backend service - there is none.
- Puzzles are generated by `scripts/` into `docs/puzzles/` in CI; the game reads only that output.
- Browser code MUST NOT import Python or build tooling.
- The client is a pure consumer of puzzle JSON: it never mutates the solution and never assumes a directory listing (it probes `YYYY-MM-DD-NNN.json` and treats a 404 as "no more puzzles").

## 6. Correction Levels

| Level | Scope | Workflow |
| :---: | ----- | -------- |
| 0 | Comments, typos, log strings | Direct fix |
| 1 | 1 file, ~50 lines, isolated bug | Direct fix |
| 2 | 1-2 files, explicit behaviour change | Plan -> execute once scope is clear |
| 3 | 2-3 files, cross-cutting | Plan -> phased execution |
| 4 | 4+ files, structural | Propose breakdown first |
| 5 | Core design / puzzle JSON or save format / generator or solver algorithm | Design consultation only - pause work |

When in doubt, choose the higher level.

## 7. Schema Versioning

Persisted surfaces: **puzzle JSON** (classic + gattai, shipped in the bundle) and **save data** (localStorage, owned by the client). See [docs/reference/data-contracts.md](docs/reference/data-contracts.md).

- Additive, backwards-compatible change: keep old payloads loading.
- Breaking change (removed field, type change, semantic shift): write the read-side migration the new client runs on older payloads, in the same commit. A player whose save from yesterday no longer loads today is a release blocker.
- The gattai puzzle carries a `version` field; the localStorage best-times format already migrates its legacy single-value key on read.

## 8. Testing

- **Python:** pytest in `tests/` (solver, validator, difficulty, generate, gattai, CLI). Real fixtures, no network at runtime.
- **JavaScript:** game-logic tests in `tests/`.
- No mocks unless explicitly requested or for a genuinely untestable boundary (e.g. `fetch` in a loader unit test).
- A behaviour-changing commit lands with the appropriate test; the full suite is green at merge.

## 9. Definition of Done

- [ ] Tests added/updated for the changed surface; full suite green locally.
- [ ] Generated puzzles still validate (unique solution) if generation changed.
- [ ] Canonical docs updated under `docs/` (right tier).
- [ ] Persisted contracts versioned/migrated if a shape changed (section 7).
- [ ] No `[DEBUG]` markers left (grep and remove; re-run tests).
- [ ] No new hardcoded tunables; no new mocks unless requested.
- [ ] For browser changes: smoke-tested in a browser (serve `docs/`, load a puzzle, check the console for new errors / 404s).

## 10. Git Hygiene

"finish / ship / merge" authorises the normal reversible workflow: inspect, named branch, stage explicit paths, commit, push, merge after gates pass.

Avoid broad / lossy / history-rewriting commands: `git stash`, `git reset --hard`, `git clean -fd`, broad `git checkout` / `restore`, `git add .` / `-A`, `git push --force`, amending pushed commits.

Commit messages describe the change. **No AI co-author / attribution tags.**

## 11. Non-Goals

- Production backend, database, user accounts, or server-backed cross-device sync. Game state is `localStorage` only.
- Real-time puzzle generation in the browser (puzzles are pre-generated in CI).
- Framework-heavy frontends (React/Vue/etc.); the client is vanilla JS with no runtime dependencies.
- Runtime telemetry / analytics / error-tracking SDKs, or any third-party script that fetches at runtime.
- Monetisation (ads, IAP, timers, pay-to-skip).
- Security-through-obscurity for solutions (they ship in the JSON by design; see [docs/architecture/overview.md](docs/architecture/overview.md)).

## 12. Anti-Patterns (do NOT)

- Reinterpret, downgrade, or scope-narrow a source or instruction the user named explicitly without surfacing it (STOP-AND-SURFACE).
- Assume a backend exists, or make the browser client authoritative over puzzle correctness.
- Generate or validate puzzles in JavaScript as the source of truth.
- Hardcode difficulty thresholds or clue ranges in the client; read the `difficulty` field already written into the puzzle.
- Store absolute or backslash paths in any persisted artifact (relative POSIX paths only).
- Commit a puzzle that is not validated to have exactly one solution.
- Swallow exceptions or silently coerce invalid input - fail fast at the boundary (validate fetched JSON and `localStorage` on read).
- Mint a new puzzle-JSON or save-data field without versioning and a read-side migration (section 7).
- Build custom retry / parsing / validation when a mature library exists; justify any custom build.
- Add a runtime dependency, framework, or SDK without naming the beneficiary feature and its cost.
- Let chat logs or `/memories/` become the source of truth for architecture - `docs/` wins.
- Skip the docs update.
